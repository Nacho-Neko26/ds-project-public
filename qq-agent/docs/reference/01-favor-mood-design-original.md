[Heading 1] QQ机器人（机器人名字） 好感度与心情系统设计方案
[Heading 2] 一、系统概述
[First Paragraph] 在QQ机器人「（机器人名字）」的整体架构中，好感度系统与心情系统构成了角色拟人化交互的核心底层逻辑。这两个系统并非孤立运行，而是与现有的怒气系统、人设引擎（Persona Engine）深度耦合，共同驱动角色在不同场景下的行为变化。
[Body Text] 好感度系统旨在模拟真实人际关系中的亲密度动态变化。它通过一套严谨的数值体系（0-100）和档位机制，将用户与机器人之间的交互历史量化为具体的行为权限（如点歌、记事、态度温和等）。该系统不仅决定了角色对用户的“底色”态度，还作为全局权重参与到其他系统的判定中。
[Body Text] 心情系统则负责赋予角色“当下”的情绪状态。它根据当天的对话内容、工作量负载以及生理节律（饱腹/困倦）动态调整角色的表达风格。如果说好感度是角色的“长期记忆与关系基石”，那么心情系统就是角色的“短期情绪与生理反馈”。
[Body Text] 这两个系统通过 agent.mjs 中的 buildPrompt() 函数，在每一轮对话前将当前状态注入到给大语言模型的 Prompt 中。模型根据这些结构化的状态标签（如【当前状态】、【她现在的脾气】、【你对这人的好感】），结合 persona.md 中的人设正文与发言规则，生成符合当前情境的回复。这种“数值驱动+Prompt注入”的架构，确保了（机器人名字）在保持赛博蓝鲸人设一致性的同时，展现出丰富、自然且符合逻辑的动态交互能力。
[Heading 2] 二、好感度系统
[Heading 3] 2.1 系统设计目标

[Body Text] 二、日常聊天与每日维护触发条件
[Body Text] 正常聊天（不命中任何正面/负面关键词）时，系统会标记 dayChatted = true。该标记是每日维护加分的前提条件。
[Body Text] 每日维护触发条件：
[Compact] 执行时间：每日 04:00 统一执行维护任务。
[Compact] 条件1：当日 dayChatted == true（即当天有过正常聊天行为）。
[Compact] 条件2：当日未触发任何负面行为（dayAngered == false），即没有 fat/rude/joke 触发。
[Compact] 两个条件同时满足时：好感度 +5（dailyChatGain）。
[Compact] 限制：单日正向收益总上限为 dailyGainCap（20），超过后不再加分。
[Body Text] 三、劝说机制触发条件详解
[Compact] 触发前提：当前处于怒气事件中（怒气等级 Lv >= 1）。
[Compact] 说话者条件：说话者的好感度 >= 70（friend档及以上）才有劝说资格。
[Compact] 消息内容条件：消息必须命中 DEFEND 正则表达式：/(别生气|原谅|算了吧|给他个机会|她也不是|他也不容易|消消气|别跟他计较)/。
[Compact] 提及目标条件：消息中必须提到被劝者（角色）的 displayName（显示名称）。
[Compact] 效果：每次成功劝说 +5 好感度。
[Compact] 限制1：单人单日通过劝说获取的收益上限为 persuadeTotalCap（20），即最多劝4次。
[Compact] 限制2：单次生气事件中，最多接受 angerPersuadeTimes（2）次劝说。
[Compact] 额外效果：成功劝说会顺手把被劝者的 tempPenalty（生气临时扣分）减少 5 点。
[Body Text] 四、生气临时扣分触发条件详解
[Compact] 触发前提：角色的怒气等级 Lv >= 2（生气状态）。
[Compact] 群聊场景：群聊中全员（不只是惹角色的人）临时扣除 angerPenaltyGroup（20）好感度。
[Compact] 私聊场景：私聊中临时扣除 angerPenaltyPrivate（10）好感度。
[Compact] 记账方式：扣分记入 tempPenalty 字段，不计入当日 -10 的扣除额度（dailyLossCap）。
[Compact] 恢复机制：角色消气（怒气回到 Lv0）后，tempPenalty 原样归还，好感度恢复。
[Compact] 注意：临时扣分是"暂扣"而非"永久扣除"，消气即还。
[Body Text] 五、半速机制触发条件详解
[Compact] 触发条件：当前好感度 favor < 50（half 阈值）。
[Compact] 效果1：所有正向收益（praise +1、每日维护 +5、劝说 +5 等）乘以 slowFactor（0.5）。
[Compact] 效果2：小数部分累积到 slowAcc 字段，当累积值 >= 1 时进位为实际好感度 +1。
[Compact] 效果3：半速状态下，单日正向收益上限从 dailyGainCap（20）降为 slowGainCap（10）。
[Compact] 负向不受影响：负面扣分（-1）不受半速系数影响，只受单日 -10 上限限制。
[Compact] 恢复：当好感度通过任何方式恢复到 >= 50 时，半速机制自动解除。
[Body Text] 六、保底机制与老档案迁移
[Compact] 主人保底：主人私聊时，强制设定 favor = max(favor, 90)，确保主人始终处于 sing（亲密）档。
[Compact] 注意：这是代码层行为，人设 persona.md 中需同步写明此规则，否则模型不知道自己处于高好感状态。
[Compact] 老档案迁移：旧版 intimacy 字段（0~5）按以下规则映射到新 favor 值：
[Compact] - intimacy 0 -> 30
[Compact] - intimacy 1 -> 40
[Compact] - intimacy 2 -> 50
[Compact] - intimacy 3 -> 62
[Compact] - intimacy 4 -> 72
[Compact] - intimacy 5 -> 80
[Body Text] 七、触发优先级与结算顺序
[Body Text] 当一条消息同时命中多个触发词时，系统按以下优先级处理：
[Compact] 优先级1（最高）：JOKE_ABOUT_ANGER（拿生气开玩笑） -> 好感 -1 + 怒气热值 +4
[Compact] 优先级2：RUDE（辱骂/贬低） -> 好感 -1 + 怒气热值 +2
[Compact] 优先级3：FAT（说胖/体重） -> 好感 -1 + 怒气热值 +2 + mood:fat
[Compact] 优先级4：praise/praiseStrong（夸奖） -> 好感 +1 + mood 变化
[Compact] 优先级5（最低）：正常聊天 -> 标记 dayChatted = true（仅作为每日维护的判定依据，不直接改变好感度）
[Compact] 注意：负面触发和正面触发不会互相抵消——一条消息中如果同时包含夸奖和辱骂，两者都会结算。
[Body Text] 八、注意事项与常见陷阱
[Compact] 注意1：praiseGain 和 offendLoss 虽然在 favor.mjs 中定义了常量，但实际值写死在 index.mjs 中（正负1）。修改 favor.mjs 里的常量不会生效，需要改 index.mjs。
[Compact] 注意2：半速机制的注释说"或者曾经掉到过20以下"，但代码只看当前 favor < 50；everBelow20 只写不读。想保留"留疤"逻辑需要补充判断。
[Compact] 注意3：生气扣分只从 Lv2 起生效，Lv1 不扣好感。这意味着 Lv1 时虽然态度变差，但不会真正伤害关系（好感度不掉），这是一个安全阀设计。
[Compact] 注意4：劝说机制中，说话者好感 >= 70 是硬性条件。好感低于 70 的人即使说了劝说的话也不会触发加成。
[Compact] 注意5：每日维护的 +5 是"基础收益"，如果处于半速状态（favor < 50），这 +5 也会乘以 0.5 变为 +2.5（小数累积进位）。
[Compact] 注意6：临时扣分（tempPenalty）和每日扣除额度（dailyLossCap）是两套独立的记账系统，互不干扰。

[Heading 3] 4.1 怒气触发词与热值机制
[First Paragraph] 怒气通过热值（Heat）累积触发，不同触发词具有不同权重：
[Compact] 自然衰减：正常说话 -1，每 6 分钟自然衰减 1 点。
[Compact] 阈值：≥3 → Lv1（烦），≥6 → Lv2（生气），≥9 → Lv3（真冷了）。
[Compact] 低好感惩罚：好感 < 20 时，阈值各降 1（2/5/8）。
[Compact] 升级规则：Lv2 再被戳直接升至 Lv3。
[Compact] 跨天清零：每日 0:00 热值重置。
[Heading 3] 4.2 怒气对好感度的影响
[Compact] Lv ≥ 2 时，群聊全员临时 -20，私聊 -10。
[Compact] 临时扣分不计入每日 -10 上限，消气后原样归还。
[Heading 3] 4.3 好感度对怒气的缓冲
[Compact] 高好感缓冲：好感 ≥ 70 的用户来搭话，怒气立刻降一档。
[Compact] 低好感易怒：好感 < 20 时，怒气阈值降低，更容易触发高级别怒气。
[Heading 3] 4.4 哄法与回落机制
[First Paragraph] 以下五种方式可使怒气回落一档： 1. 叫全名「（机器人名字）」 2. 认真道歉 3. 提饭/请吃饭（Lv2+ 直接归零） 4. 具体地夸 5. 什么都不说照常聊天（慢速回落）
[Heading 2] 五、系统交互关系
[First Paragraph] 三个核心系统通过以下数据流和触发条件形成闭环：
[Source Code] 用户消息
    │
    ├──→ [对话内容分析] ──→ 心情状态机 ──→ 注入 Prompt
    │         │                    │
    │         │                    ├──→ 触发 FAT/RUDE → 怒气热值↑
    │         │                    │
    │         └──→ 深度倾诉 → 好感度+1
    │
    ├──→ [怒气判定] ──→ 怒气等级 ──→ 临时好感扣分
    │         │              │
    │         │              └──→ 高好感用户搭话 → 怒气降档
    │         │
    │         └──→ 低好感(<20) → 怒气阈值↓
    │
    └──→ [好感度结算] ──→ 好感档位 ──→ 行为权限/语气
                  │
                  ├──→ ≥80 → 解锁记事本
                  ├──→ ≥90 → 解锁点歌
                  └──→ ≥70 → 晚安机制 / 怒气缓冲
                  
[工作量计数器] ──→ 疲劳状态 ──→ 注入 Prompt
       │
       └──→ 被夸/饭后 → 工作量↓ → 疲劳缓解
[First Paragraph] 核心交互说明：
1. 用户消息进入后，同时触发对话内容分析（心情系统）和怒气判定（怒气系统）两条并行链路。
2. 对话内容分析链路：分析消息情感倾向 -> 匹配关键词/正则 -> 更新心情状态 -> 若命中深度倾诉则好感度+1。
3. 怒气判定链路：匹配触发词 -> 累加热值 -> 判断是否跨阈值升级 -> 若Lv>=2则对好感度施加临时扣分。
4. 好感度结算链路：根据当前好感档位决定行为权限和语气 -> 若>=80解锁记事本 -> 若>=90解锁点歌 -> 若>=70参与晚安机制和怒气缓冲。
5. 工作量计数器独立运行，每日0点重置 -> 根据累积值映射疲劳状态 -> 注入Prompt影响回复风格 -> 饭后/被夸时恢复。
6. 三个系统最终通过buildPrompt()合并为统一状态块注入模型，模型根据完整上下文生成回复。

[Heading 3] 6.2 改之前值得注意的 10 个坑
[Compact] 坑1：唱歌功能已接通：config.json 里 music.enabled: true，FAVOR.sing = 90 的 sing 档已接通。人设 persona.md 中「唱歌功能后面才有」这句已过时，需同步更新。
[Compact] 坑2：主人保底90需人设同步：主人私聊好感保底90是代码行为（index.mjs），人设 persona.md 里若没写这条，模型自己不知道自己是90分，行为会不一致。要么写进人设，要么删掉代码保底。
[Compact] 坑3：群聊接话规则双写：群聊接话规则写在两处：persona.md 的「什么时候不说话」+ agent.mjs 的 rules.push(...)。改口径必须两边一起改，否则互相打架。
[Compact] 坑4：「鱼片」昵称三处同步：「鱼片」被硬编码3处：callName()默认值、index.mjs建档默认nickFor、buildPrompt里「Lv2起不再叫鱼片」。换昵称要三处一起动，漏一处就出bug。
[Compact] 坑5：slowGrowth注释与行为不符：注释说「或者曾经掉到过20以下」，代码只看当前favor<50；p.everBelow20只写不读。想保留「留疤」逻辑得补一句判断。
[Compact] 坑6：praiseGain/offendLoss实际写死：favor.mjs里定义了praiseGain和offendLoss常量，但实际值写死在index.mjs（正负1）里。改 favor.mjs 里的值不会生效，需要改 index.mjs。
[Compact] 坑7：卡片档位名与人设不一致：renderFavorCard的档位名（有点烦你/信得过）和人设分档描述（不耐烦/听他的话）措辞不一致，用户看到的是卡片那套。改一处时需同步更新另一处。
[Compact] 坑8：自称「本鲸」散落多处：自称「本鲸」散落在代码文案里：「本鲸对你的好感」「晚安本鲸也要去机柜里躺着了」「sootheHint里叫全名（机器人名字）」。改自称/改名必须全仓库搜索替换，漏一处就出戏。
[Compact] 坑9：怒气分档时间与人设微小出入：Lv1人设写「几分钟」实际8分钟；Lv2 20分钟/Lv3 30分钟是对得上的。另外「好感<20的人一开口你容易上火」实际是「热值门槛各降1」，不是一开口就上火。改怒气逻辑时注意代码与人设描述的差异。
[Compact] 坑10：生气扣分只从Lv2起生效：生气扣分只从Lv2起生效，Lv1不扣；扣分是全员（不只是惹你的人）。这意味着Lv1时虽然态度变差，但不会真正伤害关系（好感度不掉），这是一个安全阀设计。
